# DECISIONS

One line per decision, in order made. This file feeds the case study (§11) directly — write here the moment a decision is made, not from memory later.

## Session 0 — Planning review (31 Aug 2026)

- **Region: mainland France, not Valencia/Spain (the plan's original recommendation).** Valencia's station count (~20-40) is too thin for a convincing IDW surface and has no visible elevation story. France has 203 usable stations and a real elevation failure case (Alps/Pyrenees/Massif Central against a flat NW), which is the plan's own strongest talking point (§8). France is also the current job-search priority geography.

- **Data source: NOAA ISD-Lite, not Open-Meteo.** Open-Meteo serves reanalysis/model output at arbitrary coordinates, not real station observations — using it would have quietly broken the "real station data, not model output" premise the whole product argument rests on (§2 criterion 3, §11's "point data vs. the space between" framing). ISD-Lite is real observed data, no key required.

- **Reused the 2024 project's own station inventory (`isd-history.csv`) rather than pulling a fresh station list.** It already contains 381 French stations (203 active through 2024+) with id, name, lat/lon and elevation — no reason to redo work that exists.

- **v1 codebase: confirmed none survives.** Two 2024 GitHub repos (`weatherscout`, `WeatherPlace` — the project's real names at the time) each have a single commit and no working application code. Rebuilding from scratch, using the 2024 spec document as a reference, not as code.

- **v1 narrative: will be described with real specifics, not vaguely.** The actual 2024 spec (`Project descriptions.docx`) targeted isochrones, sport-condition matching, forecasting, user accounts, and a $50k/year revenue goal — and stalled, plausibly at NOAA ISD's raw fixed-width data format. This is a stronger, truer case-study opening than a vague "an earlier version I built in 2024": it directly demonstrates the scoping discipline this whole artifact exists to prove.

- **Repo: rename the existing public `weatherscout` GitHub repo to `klima`** (currently a single-commit README stub) rather than create a new one — GitHub redirects the old URL automatically, so this preserves history at zero cost. No backdated commits — a 1-2 day build history is a defensible, even favorable, answer to "how long did this take" (§12), not something to disguise.

- **IDW overlay (criterion 4, §2) confirmed mandatory, not optional under time pressure.** The original plan contradicted itself: §2 listed it as a required success criterion while §10 said to cut it first if Session 2 ran long. Resolved: the overlay is the product; a station map without it doesn't clear the bar this artifact is meant to clear. If time runs short, cut the variable selector or second variable instead.

- **Session budget revised from 12-21h to ~9-10h**, reflecting the actual build mode: Claude generates the code, Alex reviews and explains it back rather than typing it himself. Explain-back checkpoints scheduled explicitly at the end of Sessions 1 and 2 (the latter non-negotiable) so comprehension — the real constraint under this build mode — isn't assumed.

- **Data source pivoted mid-Session-0: NOAA ISD-Lite → Météo-France SYNOP.** NOAA's servers (and every other tested weather-data host — Meteostat, AWS S3 mirrors) are unreachable from Claude's cloud sandbox; its network is locked to a short allowlist (package registries only), confirmed by testing directly. Worked around this by using the browser pane inside the Claude desktop app instead, which runs on Alex's own computer with normal internet access. That reached `public.opendatasoft.com`, which mirrors Météo-France's official SYNOP network as a plain JSON API — real government station data, no key required, and richer than ISD-Lite in one important way: altitude is a native field on every reading, directly serving the elevation-limitation story in §8. Considered combining both sources; rejected — NOAA's files are gzip-compressed binaries, which even a real browser can't render as readable text (it just triggers a file download), so reaching them would need a much more fragile file-download-and-unpack path for limited additional value. Considered extending to more countries to get more stations from NOAA; rejected outright — §5 of the plan explicitly forbids multiple regions, and that's a deliberate scope boundary, not a technical one.

- **Pulled 41 real French SYNOP stations** (mainland + Corsica; overseas territories like Réunion, Martinique, Guadeloupe excluded to keep the region as scoped) via two query snapshots against `public.opendatasoft.com/api/records/1.0/search/?dataset=donnees-synop-essentielles-omm`, deduplicated by station ID, cleaned into `data/klima_stations.json`. Fields: id, name, lat, lon, elevation, temperature, humidity, wind speed, pressure, observation timestamp. Geographic spread: latitude 41.9-50.6°N, longitude -4.4 to 9.5°E (Brittany to Corsica), elevation 2-871m.

- **Data snapshot date is 2026-01-15, not "today."** The dataset's most recent available reading was from mid-January 2026, roughly 7.5 months old at time of pull. This is fine under §7's own logic (static snapshot by design, not live data) but must be stated honestly in the README and case study — "a January 2026 snapshot of the Météo-France SYNOP network," never "current" or "live."

- **Station count (41) is below the plan's original 150-250 target, revised down to ~45-60 during this session's discussion.** Real, official, well-distributed data was prioritized over hitting a specific count. If the rendered map looks too sparse in Session 1, two fallback options exist without re-opening the region/source debate: pull additional pages from the same Opendatasoft API (more historical snapshots, more stations may appear), or Alex manually downloads NOAA ISD-Lite files on his own machine (bypasses Claude's sandbox network restriction entirely) for Claude to parse.

## Session 0 — Naming and roadmap (1 Sept 2026)

- **Project renamed WeatherScout → Klima**, Alex's explicit request. Applied across the plan, STATE.md, DECISIONS.md, and the plan filename (`Klima_Project_Plan.md`). The 2024 repo names (`weatherscout`, `WeatherPlace`) are historical fact and were NOT renamed — only the going-forward project name changed. The case study should state the rename plainly rather than imply the project was always called Klima.

- **Historical/temporal climate-explorer idea: deferred to a phased roadmap, not built now.** Alex described a fuller vision — daily/monthly aggregation, a year-range and period filter, spatial color-coding by long-term average, year-over-year comparison charts. Checked against §5: a period filter is functionally the "time slider" the plan explicitly puts out of scope, and a year-over-year chart is explicitly forbidden ("any chart that is not the map"). Building it now would risk the deadline and the "finishes things" narrative that is the actual point of this artifact (§3). Resolved: documented as Phases 2-4 in the plan's new §17, with only Phase 1 (this build) in scope now. This phased vision itself becomes stronger material for the case study's "what's next" section than a single invented idea would have been.

- **Phase 1 kept forward-compatible at zero extra cost, not through speculative build-ahead.** Station data keyed by station ID (so a future historical dataset can reuse the same IDs), map/overlay written as functions taking "a dataset of per-station values" (so swapping the data source later is a data change, not a rewrite), real incremental commits instead of one giant commit. Explicitly did NOT build any filter UI, chart library integration, or historical data schema now — that would spend Phase 1's budget on Phase 2/3 features whose real shape isn't known yet, which is the same discipline error as any other premature feature build.

## Session 1 — Scaffold, map, markers (1 Sept 2026)

- **CircleMarker used instead of Leaflet's default pin icon.** Default Leaflet markers have a well-known bug with bundlers like Vite — the icon image paths break unless manually patched. CircleMarker sidesteps this entirely and, as a bonus, sets up Session 2's colour-by-temperature design for free (a circle can be recoloured; a pin icon can't as naturally).

- **No design pass yet — deliberate, not an oversight.** The current look (dark header, plain blue dots, default map background) is a functional placeholder. §10's schedule puts the real design pass in Session 3, after the interpolation overlay exists — no point polishing a look that Session 2 will materially change (colour scale, legend).

- **Verified the build with a real headless-browser screenshot before handing it off, not just "it compiled."** TypeScript compiling and Vite building clean don't prove the app actually renders correctly — ran it and looked at real output: markers traced France's outline correctly (Corsica, Brittany visible), clicking a marker (Orly) opened the correct popup with real data. Map tiles didn't load in Claude's own verification browser — same network allowlist restriction that blocked NOAA in Session 0 — confirmed via matching error patterns, not assumed; not an app bug, and it renders tiles correctly in Alex's own browser.

- **First-time Windows/Node setup friction, logged for the eventual README.** The nodejs.org download page defaults to Docker installation instructions rather than the plain Windows installer — easy to follow the wrong section. And Windows blocks PowerShell script execution by default, which breaks npm's Windows launcher until `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` is run once. Neither is specific to this project, but worth a line in the README's "how to run this" section since it'll trip up anyone else on Windows too.

- **Explain-back checkpoint passed.** Quizzed on data/code separation (does adding a station require a code change — no), the render loop (`.map()` as "for each," not cartography), and Leaflet's built-in popup behavior. 4/4 correct. Produced a reusable one-paragraph explanation for interview use.

- **Second explain-back round (deeper mechanics), also 4/4.** Covered: TypeScript interfaces are erased before runtime (compile-time-only); MapContainer (interactions) vs. TileLayer (visual tiles) are separate concerns; marker colours are set in App.tsx's code, not CSS; a one-sentence definition of what React actually is. Confirmed ready to proceed to Session 2.

## Session 2 — Interpolation overlay (1 Sept 2026)

- **Variable interpolated: temperature only, not all four readings.** Temperature is the headline variable (already the first thing shown in the header/popups) and the most intuitive to sanity-check visually. Humidity/wind/pressure interpolation would reuse the same code path with a different field — logged as an easy future extension, not built now (no new UI or filter needed, just more toggle buttons later).

- **Used all 41 stations for every grid point, no k-nearest or radius restriction.** The plan allowed either approach. With only 41 stations across the whole country, restricting to "nearest k" would exclude real signal for little performance benefit (41 distance calculations per grid point is trivial). Full IDW is also simpler to explain in an interview than a restricted variant.

- **Power parameter fixed at p=2 (the standard default), not exposed as a user control.** A power slider is a filter-style UI control — explicitly a Phase 3 idea (§17), not Phase 1. Hardcoding it keeps the scope line clean.

- **Interpolation grid bounds = the stations' own lat/lon extent + 0.5° padding, not France's political border.** Simpler to compute, and honest: IDW has no real basis for a value far outside the station network's footprint anyway. The padding just avoids the overlay clipping visually right at the outermost dots.

- **Colour scale: fixed blue→white→red diverging palette, scaled to this dataset's actual min/max (2.3°C–11.9°C on the Jan snapshot), not a fixed global range.** Standard "cold=blue, hot=red" convention needs no legend explanation in an interview. Scaling to the real min/max (rather than e.g. a fixed -10 to 40 range) keeps the full colour range visually useful on any given snapshot, at the cost of the same colour meaning a different temperature on a different day — acceptable for a single-snapshot demo, would need documenting if the app ever showed multiple dates side by side.

- **Grid computed once on mount via `useMemo` with an empty dependency array — confirmed never recomputed on pan/zoom.** Matches the plan's explicit requirement. Verified by code inspection (the `useMemo` deps array is `[]`, and the station data is a static import, not state) rather than just asserting it.

- **Verified with headless-browser screenshots, both overlay-on and overlay-off (toggle-clicked) states**, not just a successful build. Confirmed: gradient renders correctly under the markers, legend numbers match the data's real min/max, toggle button actually adds/removes both the overlay and the legend, and no app-level console errors (only the same tile-loading network restriction from Session 1, not a bug).

- **Overlay masked to France's real coastline, not left as a rectangle — Alex caught this after the first pass.** Pulled a public France boundary shape (mainland + Corsica + a few small islands, no overseas territories — confirmed by checking every sub-shape's coordinates) from a public GitHub-hosted dataset (`mledoze/countries`), saved as `data/france_boundary.json`. Added `lib/pointInPolygon.ts` (a standard ray-casting inside/outside test) and used it in `lib/overlay.ts` to make any grid cell outside France's outline fully transparent instead of painted. This is a visual-correctness fix to the interpolation overlay already in scope, not a new feature — no new UI, no new data dimension.

- **Boundary data upgraded to a higher-resolution source after Alex spotted visible misalignment when zoomed into Brittany.** The first boundary pull (`mledoze/countries`) was accurate at country scale but too coarse for a jagged coastline like Brittany's once zoomed in. Replaced it with Natural Earth's 1:10,000,000-scale country dataset, filtered down to only the European France polygons (mainland + Corsica + small coastal islands, overseas territories excluded by bounding box), nearly doubling mainland coastline detail (3,097 points vs. 534). This alone was not the fix — see below.

- **Coastline mask was limited by the colour grid's resolution, not the boundary data's — first real fix.** After the boundary-data upgrade, Alex zoomed in again and the edge was still visibly rounded/offset. The actual bug: the coastline test was being run once per COLOUR GRID CELL (240×150 cells across all of France, each ~5km wide), so however precise the underlying map data was, the mask itself could only ever be as sharp as that grid — like tracing a detailed map with a thick marker. Fixed by decoupling the two: the colour field (smooth, slowly-changing data) still uses a modest grid, but the coastline is now drawn as a true vector shape directly on the canvas and used as a clip mask (`ctx.globalCompositeOperation = 'destination-in'`), so its sharpness comes from the coastline data itself, not from grid resolution. Also bumped the colour grid from 240×150 to 640×400 for a smoother gradient, cheap to do since IDW's cost scales with grid cells × stations (41), not with coastline complexity. `lib/pointInPolygon.ts` (the earlier per-cell ray-casting approach) is no longer used and can be deleted.

- **Second, deeper bug found after Alex reported the overlay still looked shifted: a map-projection mismatch, not a data problem.** Leaflet displays the map using the Web Mercator projection, which stretches the map vertically more the further from the equator — the same reason Greenland looks oversized on a world map. Our overlay image was built with rows evenly spaced by DEGREES of latitude (a plain equirectangular grid), then handed to Leaflet, which stretches that image uniformly to fit its Mercator-projected bounds — a mismatch between "evenly spaced in degrees" and "evenly spaced in Mercator's own scale." Quantified it numerically before fixing: across France's ~9.6° latitude span (with padding), the error between linear-degree spacing and true Mercator spacing peaks at roughly 20-25km in the middle latitudes (near Brittany), and is exactly zero at the very top and bottom edges — matching precisely what Alex saw (a shift that grows away from the edges). This is a well-known gotcha specific to draping a raster image over a Mercator slippy map, not a data-quality or model-capability issue. Fixed by spacing the overlay's rows evenly in Mercator space instead of degrees (`idw.ts`'s `computeIDWGrid` and `latToRowFraction`), and using that same conversion for the coastline vector path in `overlay.ts` so both layers agree. Verified numerically (round-trip row↔latitude conversion accurate to floating-point precision) since Claude's own browser still can't render real map tiles to compare against directly — final visual confirmation is Alex's.

## Session 3 — Design pass, polish (1 Sept 2026)

- **Tile theme switched from default OpenStreetMap to CARTO Positron, a muted/light basemap.** Plan §10 explicitly called for "one deliberate cartographic theme, not default Leaflet grey." Default OSM tiles are fairly saturated (green parks, yellow/orange roads) and visually compete with the red/blue temperature overlay. Positron is free, requires no API key, and is a standard choice specifically because a quiet basemap lets a data layer be the visual focus — a real cartographic/data-viz principle, not just an aesthetic preference.

- **No variable selector built.** Plan §10 said "only if it's free." Right now only temperature has a computed IDW overlay; a working selector for humidity/wind/pressure would mean building and testing three more overlay computations, which is real scope, not a free addition. Deferred — same reasoning as the Phase 2/3 roadmap in §17.

- **"About this project" panel added as a small in-app overlay, not a separate page.** Content: what the map shows, the IDW method in one sentence, the data snapshot date, and the elevation limitation stated upfront (per the case-study principle in plan §11: state limitations first, rather than let an interviewer find them). Kept to plain text, no external links yet — the GitHub URL isn't final until the repo rename/push happens.

- **Mobile layout handled with CSS media queries only, no new dependencies** — consistent with plan §6's styling rule (plain CSS, no component library). Verified with headless-browser screenshots at a 375px-wide viewport (iPhone-sized): header, both control buttons, legend, and the About panel all stay legible and non-overlapping. The two control buttons wrap onto a second row on very narrow screens rather than overflowing or shrinking unreadably.

- **README.md rewritten from the default Vite template** to plan §9's spec: what it is, the stack, data source and attribution, and how to run it locally — including the Windows Node.js/PowerShell friction points logged back in Session 1, so a future reader (or interviewer cloning the repo) doesn't hit the same issues blind. Left a placeholder for the live deploy URL, to be filled in once Session 3's deploy step completes.

- **GitHub push: kept the renamed repo's original 2024 stub commit instead of overwriting it.** The `weatherscout`→`klima` rename brought along one pre-existing commit (an empty README) with no shared history with the freshly-built local repo, so `git push` was rejected outright. Two ways to resolve it: force-push (erases the old commit) or pull with `--allow-unrelated-histories` and merge (keeps it). Chose to merge — the old commit is real project history and directly reinforces the "honest v1→v2" narrative this whole project already leans on (§0's own reasoning for renaming rather than creating a new repo). Resulted in one small merge commit and a real, if slightly unusual, git history — worth explaining plainly in an interview rather than hiding.

- **Tile theme switched a second time, from CARTO Positron to standard OpenStreetMap — discovered only after deploying, not in local dev.** The live Vercel deployment showed the map tiles replaced by a diagonal "API KEY REQUIRED" watermark. Confirmed via web search this is a real, recent, and fairly widely-hit issue (the same watermark has broken map integrations in Home Assistant, Grafana, and openHAB) — CARTO's basemap tile service, previously usable anonymously, now requires a free account and API key. Rather than add an account/key dependency (against the plan's own "buy nothing," keep-it-simple spirit, and a dependency that could silently break again), switched to standard OpenStreetMap raster tiles, which need no key and no account. Genuine lesson for the case study: a free third-party service can change its terms without warning, and local `npm run dev` didn't catch it — only testing the actual deployed production build did, which is itself a good argument for why deploying early and checking the real thing matters.

## Session 5 — Elevation correction, closing V2 (2 Sept 2026)

- **Elevation correction added to V2 rather than deferred to a later version.** It was the one limitation the case study itself led with, it's bounded (a better calculation, no new UI, no new interaction), and it's the piece most tied to Alex's own domain background. Everything else on the v3 candidate list (variable selector, historical data, more countries) stays out.

- **Method: lapse-rate corrected IDW ("detrended" IDW), not a new interpolation algorithm.** Three steps: convert each station's reading to its sea-level equivalent by adding back the cooling its own altitude caused; run exactly the same IDW blend on those sea-level values; then subtract the cooling again at each grid point using that point's real ground height. The interpolation itself is untouched — only what gets interpolated changed. Standard lapse rate of 6.5°C per 1,000m. This matters more than it sounds: no station in the dataset sits above 871m, so the previous version was effectively painting valley temperatures across a 4,000m mountain range.

- **Elevation data sourced live from a public DEM API and baked into a static file, not fetched at runtime.** Consistent with the existing no-backend/no-runtime-API rule (§5). A 78 × 120 grid (~14km spacing) over the map's bounds, bundled as `data/france_elevation.json` and bilinearly interpolated at lookup time. 14km is deliberately coarse: it resolves the Alps, Pyrenees and Massif Central as the large landforms they are, which is all this map can display, without shipping a multi-megabyte terrain file for detail nobody sees.

- **Elevation source switched mid-fetch from Open-Meteo to OpenTopoData (SRTM 90m), and the already-fetched half was thrown away rather than stitched.** Open-Meteo's free tier hit its hourly request limit ~40% of the way through. Rather than complete the remaining points from a second provider, re-fetched everything from OpenTopoData: mixing two different digital elevation models across one map risks a systematic step where the two datasets meet, and a visible seam through the middle of France would be a much more expensive problem to explain than two extra minutes of fetching.

- **Colour scale re-anchored to the estimated surface's 1st–99th percentile, instead of the station readings' min/max.** With height correction the surface now goes far colder than any station ever measured (stations: 2.3–11.9°C; corrected surface: well below zero at altitude), so scaling to station readings would have clipped every mountain to one flat blue. Using the outright min/max instead would have gone the other way — a handful of the highest cells stretching the ramp until lowland France collapsed into a single shade. Percentile anchoring keeps contrast where nearly all the map is, and lets the few extreme cells saturate.

- **Honest limitation restated rather than removed.** The About panel previously said "IDW doesn't account for elevation." That's now false, so it was replaced rather than deleted — with the real remaining caveat: 6.5°C/1,000m is a standard average, and on a still winter morning (which this 15 Jan 09:00 snapshot is) cold air pools in valleys and the relationship can locally invert. Fixing a limitation and leaving the "known limitations" section empty would have been the worse outcome.

- **Found and fixed a structural bug: the actual git repository root is `Klima/app/`, not the parent `Klima/` folder — meaning DECISIONS.md, STATE.md, Klima_Project_Plan.md, and CASE_STUDY.md had never actually been part of the GitHub repo at all, despite README.md linking to them as if they were.** `git init` was run inside `app/` back in the deploy session, so that's the true repo root; everything one level up (where these docs live, alongside `Old code/` and a few earlier planning drafts) was never tracked or pushed. Caught when Alex ran `git status` from the parent folder and got "not a git repository." Fixed by copying the four docs into `app/` (alongside README.md, which was already correctly inside the repo) so they match what the README has been promising the whole time. `INTERVIEW_PREP.md` deliberately stays outside `app/`, at the parent level — being outside the repo folder entirely is a simpler, more foolproof way to keep it private than a `.gitignore` rule.
